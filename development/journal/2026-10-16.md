### Project overview

`ukvet-mcp` exposes Companies House data as MCP tools for an
MCP-compatible assistant such as Claude Desktop.

The eight tools documented for the server are:

1.  `search_company` --- search for companies.
2.  `get_company_profile` --- retrieve a company profile.
3.  `get_officers` --- retrieve company officers.
4.  `get_officer_appointments` --- retrieve an officer's appointments.
5.  `get_persons_with_significant_control` --- retrieve persons with
    significant control.
6.  `get_charges` --- retrieve company charges.
7.  `get_insolvency` --- retrieve insolvency information.
8.  `get_filing_history` --- retrieve filing history.

The server requires a Companies House API key supplied through the
`CH_API_KEY` environment variable.

### Adding ukvet-mcp to Claude Desktop

The intended user workflow is to configure Claude Desktop to launch the
installed `ukvet-mcp` package as an MCP server.

1.  Obtain an API key from Companies House.
2.  Ensure Python and `uv` are installed and available on the machine.
3.  Open Claude Desktop's MCP configuration file using the configuration
    location appropriate to the operating system and Claude Desktop
    version.
4.  Add a server entry that launches the published package and supplies
    `CH_API_KEY`.
5.  Replace the placeholder API key with the user's own key. Do not
    commit the key to source control or share it in screenshots.
6.  Save the configuration and restart Claude Desktop.
7.  Confirm that the `ukvet-mcp` tools appear in Claude Desktop, then
    test a simple company search and a company profile lookup.

A typical configuration entry for a package launched through `uvx` looks
like this. The exact configuration-file location and accepted schema
should be checked against the installed Claude Desktop version and the
package's current setup guide.

``` json
{
  "mcpServers": {
    "ukvet-mcp": {
      "command": "uvx",
      "args": ["--from", "ukvet-mcp", "ukvet-mcp"],
      "env": {
        "CH_API_KEY": "YOUR_COMPANIES_HOUSE_API_KEY"
      }
    }
  }
}
```

Replace `YOUR_COMPANIES_HOUSE_API_KEY` with the real key on the local
machine. Keep it private. If Claude Desktop does not start the server,
check that `uvx` is available, the package entry point is correct, the
API key is valid, and the configuration file is valid JSON. Restart
Claude Desktop after configuration changes.

### Publishing workflow

The release workflow is stored at:

`.github/workflows/release-mcp.yml`

The workflow builds the package and runs tests before publishing.
Publishing is performed through GitHub Actions Trusted Publishing rather
than a long-lived PyPI token.

The workflow has two publishing destinations:

-   **TestPyPI** --- for testing a new release before production.
-   **PyPI** --- the production package index.

The intended release process is:

1.  Update the package version in `packages/ukvet-mcp/pyproject.toml`.
2.  Update and check `packages/ukvet-mcp/README.md`.
3.  Commit and push the changes to GitHub.
4.  Open **GitHub → Actions → Release ukvet-mcp → Run workflow**.
5.  Select `testpypi` to publish a test release.
6.  Verify the package installation and project page on TestPyPI.
7.  When ready for a public release, publish to production PyPI using
    the configured workflow or the matching release tag, following the
    repository's release procedure.

A normal push to `main` does not itself publish a release. In this
workflow, a manual run targeting `testpypi` publishes to TestPyPI, a
manual run targeting `pypi` publishes to production PyPI, and pushing a
matching `ukvet-mcp-vX.Y.Z` tag triggers the production publishing path.
Do not push a release tag until the package is ready to be published
publicly.

### Release lessons and troubleshooting

#### A distribution filename cannot be reused

TestPyPI rejected a second upload of:

`ukvet_mcp-0.0.1-py3-none-any.whl`

The server reported that the file already existed. This is expected
package-index behaviour: uploaded distribution files are immutable and
cannot be overwritten with a changed README or rebuilt artifact.

**Resolution:** increment the package version to an unused version,
rebuild, and upload the new release. Check both the version and the
distribution filenames before rerunning the publishing workflow.

#### Git rejected the push

The push to `main` was rejected because the remote repository had
commits not present in the local branch.

**Safe recovery approach:**

``` powershell
git status
git pull --rebase origin main
git push -u origin main
```

If there are uncommitted changes, save or commit them first. If a rebase
conflict occurs, resolve the conflict carefully before continuing. Avoid
force-pushing because it may overwrite remote work.

#### The demo GIF is not visible on TestPyPI or PyPI

The demo GIF is not appearing on the published package pages on TestPyPI
or production PyPI, even though the README includes a direct
GitHub-hosted GIF URL:

`https://raw.githubusercontent.com/FraidoonOmarzai/ukvet/main/docs/ukvet-demo.gif`

This is a README presentation issue and is separate from whether the
package upload workflow succeeds. Check the GIF URL directly in a
browser. The README shown on each package index comes from the metadata
uploaded with that release, so changes to the repository README do not
update an already-published release. If the README needs to change,
publish a new unused package version. If the GIF URL works but the
package page still does not render it, try an HTML `<img>` tag or use a
clickable link to the media as a fallback.

The README references the GIF hosted in the GitHub repository:

`https://raw.githubusercontent.com/FraidoonOmarzai/ukvet/main/docs/ukvet-demo.gif`
